```bash

```

### В чём была причина
Причина заключалась в недостаточных правах пользователя homework на каталог: /var/lib/linux-devops-homework

Приложение server.py пыталось создать или изменить файл: /var/lib/linux-devops-homework/startup.log

Но пользователь homework, от имени которого работает systemd-сервис, не имел необходимых прав на запись в этот каталог.

```bash
# изменения и/или команды
sudo chown -R homework:homework /var/lib/linux-devops-homeworkv
```
Изменил владельца и группу /var/lib/linux-devops-homework
### Почему было выбрано это решение
Сервис настроен на запуск от имени пользователя homework.Поэтому нужно предоставить этому пользователю права на каталог, в который приложение должно записывать данные.
Изменять пользователя сервиса на root было бы неправильным, поскольку это дало бы приложению избыточные системные права.

## Проблема 3.

### Что было обнаружено

При проверке прав доступа к каталогу состояния приложения `/var/lib/linux-devops-homework` было обнаружено, что каталог имеет права доступа `700`, тогда как по требованиям задания должны быть установлены права `750`.

Это ограничивало доступ к каталогу только его владельцем и не предоставляло группе необходимые права на чтение и выполнение.

### Как проводилась диагностика

```bash
ls -ld /var/lib/linux-devops-homework
```

### В чём была причина

Причиной проблемы являлись некорректные права доступа к каталогу состояния приложения. Значение `700` предоставляет владельцу полные права, но не предоставляет никаких прав группе и остальным пользователям.

Для данного каталога требовалось значение `750`, при котором владелец имеет полный доступ, группа может читать содержимое и обращаться к каталогу, а остальные пользователи не имеют доступа.

### Что было изменено

Для установки необходимых прав доступа была выполнена команда:

```bash
sudo chmod 750 /var/lib/linux-devops-homework
```

### Почему было выбрано это решение

Команда `chmod 750` позволяет установить требуемые права доступа без изменения владельца каталога.

Такое решение соответствует принципу минимально необходимых привилегий.
### Как проверялся результат

После изменения прав была выполнена повторная проверка:

```bash
ls -ld /var/lib/linux-devops-homework
```

В выводе должны отображаться права `drwxr-x---` и владелец с группой `homework homework`.

Таким образом, права доступа к каталогу были приведены в соответствие с требованиями задания.

## Проблема 4.

### Что было обнаружено

При проверке сетевых настроек приложения было обнаружено, что сервис должен принимать подключения на TCP-порту `8080` через все IPv4-интерфейсы (`0.0.0.0:8080`), однако первоначально он был привязан только к локальному интерфейсу `127.0.0.1:8080`.

В результате приложение принимало подключения только с самой машины, что не соответствовало требуемой конфигурации задания.

### Как проводилась диагностика

```bash
ss -ltnp
```

В выводе была обнаружена строка:

```text
127.0.0.1:8080
```

Это означало, что приложение слушало порт `8080` только на локальном интерфейсе.

Затем была проверена конфигурация приложения:

```bash
cat /etc/linux-devops-homework/app.conf
```

В файле обнаружены следующие параметры:

```ini
[server]
host = 127.0.0.1
port = 8080
```

Приложение использовало локальный IP-адрес в качестве адреса прослушивания.

### В чём была причина

Причиной проблемы являлось неправильное значение параметра `host` в конфигурационном файле `/etc/linux-devops-homework/app.conf`.

Значение `127.0.0.1` обозначает loopback-интерфейс, предназначенный для локальных соединений. Для прослушивания порта на всех IPv4-интерфейсах необходимо использовать адрес `0.0.0.0`.

### Что было изменено

Был открыт конфигурационный файл приложения:

```bash
sudo vim /etc/linux-devops-homework/app.conf
```

Значение параметра `host` было изменено с `127.0.0.1` на `0.0.0.0`.

Итоговая конфигурация:

```ini
[server]
host = 0.0.0.0
port = 8080
```

После изменения конфигурации сервис был перезапущен:

```bash
sudo systemctl restart homework-app.service
```

### Почему было выбрано это решение

Параметр `host` определяет сетевой адрес, на котором приложение принимает входящие соединения.

Адрес `127.0.0.1` ограничивает прослушивание локальным интерфейсом. Адрес `0.0.0.0` позволяет приложению слушать указанный порт на всех доступных IPv4-интерфейсах.

Изменение параметра `host` позволяет устранить причину проблемы без изменения исходного кода приложения и конфигурации systemd.

### Как проверялся результат

После изменения конфигурации и перезапуска сервиса была выполнена повторная проверка сетевых портов:

```bash
sudo ss -ltnp | grep ':8080'
```

В результате приложение стало слушать порт на адресе:

```text
0.0.0.0:8080
```

## Итоговый ход диагностики

Работа началась с проверки состояния `homework-app.service`. Сервис не запускался из-за неправильного параметра `ExecStart`: systemd пытался выполнить приложение по некор
ректному пути. Дополнительно выяснилось, что изменения в файле unit из репозитория не применялись автоматически, поскольку systemd использовал установленную копию в `/etc
/systemd/system/`. После исправления пути к приложению, переноса конфигурации и выполнения `systemctl daemon-reload` ошибка запуска `203/EXEC` была устранена.

После этого приложение завершалось с ошибкой `PermissionError` при попытке записать файл `/var/lib/linux-devops-homework/startup.log`. После `journalctl` выяснилось , что пользователю `homework` не хватало прав на каталог. Для устранения проблемы владельцем каталога был назначен `homework:homework`.

Затем при проверке требований задания обнаружилось несоответствие прав доступа к каталогу: вместо требуемого значения `750` использовалось `700`. Права были проверены командами `ls -ld`, после чего исправлены с помощью `chmod 750`.

На следующем этапе была обнаружена неправильная сетевая конфигурация: приложение слушало порт `8080` только на локальном интерфейсе `127.0.0.1`, тогда как по требованиям 
задания оно должно было принимать подключения на всех IPv4-интерфейсах. В файле `/etc/linux-devops-homework/app.conf` параметр `host` был изменён на `0.0.0.0`, после чего
перезапустил сервис и проверил адрес прослушивания командой `ss -ltnp`.

В конце проверочный скрипт `check.sh` завершился успешно.
